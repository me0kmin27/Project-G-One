# 기존 저장소 현황 감사

## 1. 감사 목적과 방식

재작업 전에 기존 산출물의 보존 가치와 위험을 분리하기 위해 Git 추적 파일, 최근 변경
이력, Python/.NET 프로젝트 설정, Compose 배포, API 라우트, CI와 핵심 문서를 정적
검토했다. 파일 또는 Git 이력은 삭제하지 않았으며 런타임·운영 환경에는 접근하지 않았다.

## 2. 현재 자산

| 영역 | 현재 자산 | 재작업 판단 |
| --- | --- | --- |
| 서버 API | Python 3.12, FastAPI, SQLAlchemy, Alembic | 도메인 시험 자료로 보존 후 모듈 경계를 재설계 |
| 데이터베이스 | 개발 SQLite, 운영 MariaDB 11.4 | 마이그레이션 개념은 보존, 운영 DB 선택은 PostgreSQL로 변경 제안 |
| VPN | WireGuard 구성 및 피어 API | 정책 모델 참고, 웹 컨테이너 직접 특권 구조는 교체 |
| 웹 UI | 단일 정적 관리 콘솔 | 관리자·사용자 웹 분리 요구에 맞게 교체 |
| Windows | .NET 8 WPF 단일 UI 실행 파일, CI artifact 배포 | API 계약 참고, 웹 기반 통합 배포와 UI/특권 서비스 분리 구조로 교체 |
| 파일 연결 | 문서·일부 응답 모델 | 실사용 SMB 연결/회수 및 파일 서버 ACL 연동 미구현 |
| 원격 지원 | 요청·동의 API | 데이터면과 Windows 런타임 미구현 |
| 배포 | Docker Compose, MariaDB, 설치·관리 스크립트 | 단일 명령 운영 원칙은 보존, 권한 분리와 복구 절차 재설계 |
| CI | Python 테스트, Compose 검증, Windows 패키징 | 새 디렉터리와 보안 검사 기준으로 재작성 |

## 3. 요구사항과의 주요 차이

### 3.1 서버/클라이언트 경계

현재 저장소는 최상위 서버 파일과 `windows/`를 구분하지만, 서버 내부의 도메인·인프라
경계가 약하고 Windows 클라이언트는 UI 프로세스가 VPN과 연결 작업을 직접 담당한다.
재작업에서는 `server/`와 `client-windows/`를 최상위에서 분리하고 Windows 서비스에만
제한된 특권 작업을 맡긴다.

### 3.2 서버 특권

현재 Compose 웹 서비스는 루트 사용자, `NET_ADMIN`, IP forwarding과 WireGuard 구성
볼륨을 함께 가진다. 웹 애플리케이션 취약점이 네트워크 관리자 권한으로 확대될 수 있으므로
웹/API와 VPN·방화벽 적용 서비스를 분리해야 한다.

### 3.3 파일 서버의 실제 역할

기존 방향에는 G-One이 파일 서비스를 제공하는 것처럼 읽힐 수 있는 부분이 있다. 확정된
요구사항은 내부망의 **별도 파일 서버**에 대한 접근을 VPN과 정책으로 제어하는 것이다.
G-One은 파일 데이터를 저장하거나 프록시하지 않고 파일 서버의 ACL도 우회하지 않는다.

### 3.4 신원과 장치 신뢰

현재 내장 로그인과 HS256 토큰은 테스트베드 수준이다. 운영 설계는 웹 사용자 세션,
Windows 장치 자격 증명, VPN 피어 키와 파일 서버 자격 증명을 서로 다른 수명 주기로
취급하고, AD/LDAP/OIDC 연동 시에도 내부 주체 ID와 매핑해야 한다.

### 3.5 원격 지원

요청과 동의 상태 모델은 있으나 화면·입력 데이터면, 종단 간 보호, 권한별 동의, Windows
보안 데스크톱, 세션 종료 보장이 구현되지 않았다. 프로토콜을 확정하기 전 별도 기술
검증이 필요하다.

### 3.6 Windows 프로그램 배포

현재 Windows 프로그램은 GitHub Actions artifact로 제공되어 관리자가 G-One 웹에서 VPN과
파일 서버 정책을 정하고 사용자에게 내려받게 하는 흐름이 없다. 재작업에서는 외부 artifact
직접 전달을 제품 흐름에서 제거하고, 관리자 배포 프로필과 인증된 사용자 다운로드, 일회성
장치 등록 및 감사 기록을 서버 기능으로 구현해야 한다.

## 4. 보존할 개념

- Git 이력과 기존 코드는 재작업 근거 및 회귀 참고 자료로 보존한다.
- 장치별 VPN 피어, 제한된 라우트, 티켓/동의 상태 머신, 감사 이벤트 개념을 유지한다.
- 반복 실행 가능한 설치·관리 명령과 자동화 테스트 원칙을 유지한다.
- 데이터베이스 스키마는 항상 명시적 마이그레이션으로 변경한다.
- 인증 성공과 VPN/파일 공유 같은 부가 기능 실패를 분리한다.

## 5. 폐기 또는 교체 후보

아래 항목은 아직 삭제하지 않았으며 구현 단계 승인 후 교체한다.

- 웹 프로세스에 루트/`NET_ADMIN`을 부여하는 Compose 구조
- 서버 코드가 단일 대형 API 모듈에 집중된 구조
- 관리자와 사용자가 같은 정적 웹 앱을 사용하는 구조
- Windows UI 프로세스가 VPN 설치·터널을 직접 제어하는 구조
- 빌드 시 외부 설치 파일을 검증 정보 없이 내려받아 포함하는 구조
- GitHub artifact를 사용자가 직접 받아야 하는 별도 Windows 배포 흐름
- 장기 공유 비밀 기반 HS256 운영 인증
- 테스트베드 구현을 운영 준비 완료로 오해하게 하는 현황 표현

## 6. 결론

기존 구현은 요구사항 탐색용 프로토타입으로는 가치가 있지만, 확정된 배포·권한 경계에
그대로 확장하면 반복 수정과 특권 집중이 발생한다. 다음 단계에서는 기존 Git 이력을
유지한 채 새 최상위 구조를 만들고, 검증된 계약이나 테스트만 선택적으로 이식하는 방식을
권장한다.
